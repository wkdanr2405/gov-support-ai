# 06. 용어 쉬운 설명 (발표 질의응답용)

대학 학부생이 이해할 수 있는 수준으로 정리했다. 슬라이드에 나온 용어와 개발 과정에서 쓴 AI·코딩 용어를 모두 담았다.


## AI 개념

| 용어 | 쉬운 설명 | 우리 서비스에서는 |
|---|---|---|
| LLM (대규모 언어 모델) | 글을 읽고 쓰는 AI. ChatGPT, Claude 같은 것. | 계산 결과와 공고를 읽고 대표님이 이해하기 쉬운 설명을 쓴다. 금액 계산은 하지 않는다. |
| 프롬프트 | AI에게 보내는 지시문. 질문과 참고 자료를 함께 담는다. | 계산 결과(JSON)와 '쉬운 말로 설명해 줘'라는 지시를 묶어 Claude에게 보낸다. |
| 토큰 | AI가 글을 처리하는 단위(단어 조각). 쓰는 토큰이 많을수록 비용이 늘어난다. | 리포트 1건당 입력 약 8천, 출력 약 1천 토큰으로 비용을 추정했다. |
| 환각 (할루시네이션) | AI가 그럴듯하게 틀린 내용을 지어내는 현상. | 금액은 규칙 엔진이 계산하고, 공고는 링크로 근거를 보여 주어 막는다. |
| 학습 vs 검색 | 학습은 AI가 자료를 미리 공부해 두는 것, 검색은 필요할 때 자료를 찾아보는 것. 시험 전에 외우기와 오픈북 시험의 차이. | 공고는 매일 바뀌어서 학습시키지 않고 그때그때 검색한다 (슬라이드 9번). |
| 파인튜닝 | 이미 만들어진 AI를 우리 자료로 추가 훈련해 성격을 바꾸는 것. | 하지 않는다. 비용이 크고, 바뀌는 공고를 따라가기 어렵다. |
| RAG (검색 증강 생성) | AI가 답하기 전에 관련 자료를 먼저 찾아 읽게 하는 방식. 오픈북 시험. | 공고를 먼저 찾고(검색), 그 공고만 근거로 AI가 설명한다(생성). |
| 규칙 엔진 (규칙 기반) | 정해진 규칙(법 조문)대로만 계산하는 프로그램. AI가 아니라 같은 입력에는 항상 같은 답이 나온다. | 세액공제 금액을 계산하는 Track A. |
| OCR | 이미지·스캔 속 글자를 읽어 텍스트로 바꾸는 기술. | 향후 재무제표 파일을 올리면 숫자를 자동 입력하는 데 쓴다 (가상 서류 시연은 5주차 선택 기능). |

## 검색·임베딩

| 용어 | 쉬운 설명 | 우리 서비스에서는 |
|---|---|---|
| 임베딩 | 글의 뜻을 숫자 목록으로 바꾸는 기술. 뜻이 비슷한 글은 비슷한 숫자가 된다. | 슬라이드 9번의 '공고문 임베딩'. 1단계 프로토타입은 쓰지 않고 조건·키워드로 먼저 찾는다. |
| 벡터 | 숫자를 줄지어 놓은 목록. 임베딩의 결과물이다. 지도 위의 좌표처럼 '위치'로 생각하면 된다. | 공고마다 벡터가 생기고, 가까운 벡터가 뜻이 비슷한 공고다. |
| 벡터 DB | 벡터를 저장하고 비슷한 것을 빨리 찾아 주는 저장소. | 슬라이드의 'DB 구축'이 이것. 1단계에서는 만들지 않는다. |
| 유사도 (코사인 유사도) | 두 벡터가 얼마나 비슷한지 재는 점수. | 임베딩을 쓰게 되면 기업 조건과 공고의 유사도로 순위를 매긴다. |
| 키워드 검색 vs 의미 기반 검색 | 키워드 검색은 같은 단어가 있어야 찾고, 의미 기반 검색은 말이 달라도 뜻이 같으면 찾는다. | 1단계는 키워드 점수. '청년 채용'을 '젊은 인력 고용'으로 쓴 공고를 놓칠 수 있는 한계가 있다. |
| 청킹 | 긴 문서를 검색하기 좋게 짧은 조각으로 나누는 것. | 공고문을 임베딩할 때 필요하다 (현재 미사용). |
| 필터링 쿼리 | '업종=제조업, 지역=서울'처럼 조건으로 데이터를 걸러 달라는 요청. | 업력·지역·업종 조건으로 공고를 먼저 거른다 (슬라이드 9번). |
| 쿼리 | 데이터 저장소에 던지는 질문 또는 요청문. | 필터링 쿼리와 API 요청이 모두 쿼리다. |
| Top-N | 점수가 높은 상위 N개만 보여 주는 것. | 추천 공고 상위 몇 건. |
| 매칭 점수 | 기업 조건과 공고가 얼마나 맞는지 나타낸 점수. | 조건 일치 여부와 키워드 겹침을 더해 계산하고, 근거 키워드를 함께 보여 준다. |

## 데이터 수집

| 용어 | 쉬운 설명 | 우리 서비스에서는 |
|---|---|---|
| 크롤링 | 프로그램이 웹사이트를 돌아다니며 페이지를 자동으로 수집하는 것. 도서관의 모든 책 표지를 사진 찍는 일. | 쓰지 않는다. 화면이 바뀌면 깨지고, 사이트가 막을 수 있다. |
| 스크래핑 | 수집한 페이지에서 필요한 부분(제목, 마감일 등)만 뽑아내는 것. | 크롤링과 함께 쓰이며, 우리는 API로 대신한다. |
| API | 프로그램끼리 정보를 주고받는 공식 창구. 크롤링이 창문 너머로 훔쳐보기라면 API는 접수창구. | K-Startup·기업마당 공고를 받아오고 Claude에게 설명을 요청할 때 쓴다. |
| API 키 | 그 창구를 쓸 수 있는 개인 비밀번호. | 발급받아 .env나 배포 서비스의 secrets에만 넣는다. |
| 호출 한도 (레이트 리밋) | API를 하루 또는 분당 몇 번까지 쓸 수 있는지의 제한. | K-Startup 개발계정은 하루 10,000건. 한도를 넘지 않게 저장본을 쓴다. |
| robots.txt | 사이트가 자동 수집 프로그램에게 '여기는 오지 마세요'라고 적어 둔 안내 파일. | 정부 사이트 중 일부가 이 규칙으로 자동 접근을 막아서 공식 API를 쓰는 것이 맞다. |
| 스냅샷 (저장본) | API 결과를 미리 저장해 둔 사본. | 발표 중 인터넷이나 서버 문제가 생겨도 시연이 되게 한다. |
| 캐시 | 한 번 가져온 결과를 잠깐 저장해 두었다가 다시 쓰는 것. | 같은 공고를 매번 다시 가져오지 않게 한다. |
| 실시간 반영 | 법령 개정이나 새 공고를 자동으로 가져와 서비스에 반영하는 것. | 향후 발전 항목. 지금은 수치 파일(YAML)을 사람이 갱신한다. |

## 데이터 형식

| 용어 | 쉬운 설명 | 우리 서비스에서는 |
|---|---|---|
| 데이터베이스 (DB) | 정보를 정리해 저장하고 꺼내 쓰는 저장소. | 사용자 입력은 저장하지 않는 것이 원칙이라 최소한으로만 쓴다. |
| SQLite | 파일 하나로 쓰는 가벼운 DB. | 저장이 필요할 때 쓰는 후보. |
| JSON | 프로그램끼리 데이터를 주고받는 글자 형식. {"이름": "값"} 모양. | API 응답과 계산 결과를 AI에게 넘길 때 쓴다. |
| YAML | 사람이 읽기 쉬운 데이터 형식. | 법령 수치 파일(2026.yaml)과 정답 사례가 이 형식이다. |
| 파싱 | 받은 글자 덩어리를 프로그램이 쓸 수 있게 항목별로 쪼개는 것. | API 응답에서 공고명, 접수기간 등을 꺼낼 때. |
| 스키마 | 데이터가 어떤 항목으로 이뤄졌는지 적은 설계도. | CompanyProfile, TaxResult, MatchResult 형식. |

## 개발 도구

| 용어 | 쉬운 설명 | 우리 서비스에서는 |
|---|---|---|
| Python | 이 프로젝트를 만든 프로그래밍 언어. | 계산 엔진, 공고 매칭, 화면이 모두 Python이다. |
| 라이브러리 (패키지) | 남이 만들어 둔 기능 묶음. 가져다 쓰면 처음부터 만들지 않아도 된다. | pandas(표 처리), pyyaml(YAML 읽기), anthropic(Claude 호출). pip install로 설치한다. |
| 프레임워크 (Streamlit) | 프로그램의 뼈대를 미리 만들어 둔 도구 모음. | Streamlit이 파이썬만으로 웹 화면을 만들어 준다. |
| 가상환경 (.venv) | 프로젝트마다 따로 쓰는 도구 상자. 다른 프로젝트와 버전이 섞이지 않는다. | 내 PC에서 실행할 때만 필요하다. |
| 환경변수 (.env) | 비밀번호와 API 키를 코드와 분리해 두는 파일. | 키가 코드나 GitHub에 올라가지 않게 한다. |
| 하드코딩 | 값을 코드 안에 직접 박아 넣는 것. 바꾸려면 코드를 고쳐야 한다. | 법령 수치는 하드코딩하지 않고 YAML에 둔다. |
| 모듈 | 기능별로 나눈 코드 묶음. | tax_engine, matching, data_sources, report. |
| 테스트 (pytest) | 정답을 미리 적어 두고 프로그램 결과가 맞는지 자동으로 채점하는 방법. | 코드를 바꿀 때마다 돌려서 실수를 잡는다. 현재 35개 통과. |
| TDD (테스트 먼저) | 코드를 짜기 전에 정답 테스트부터 만드는 방식. | Track A를 이렇게 만들었다. 정답은 손으로 계산해 엔진과 독립적이다. |
| 프로토타입 / MVP | 시연용 시제품 / 핵심만 담은 최소 제품. | 이번 과제는 프로토타입이다. 로그인·결제는 없다. |
| 엔드투엔드 (E2E) | 입력부터 최종 결과까지 처음부터 끝까지 한 번에 돌아가는 것. | 4주차 11/29 점검 목표. |
| Git / 저장소 / GitHub | 코드의 변경 이력을 기록하는 도구 / 코드 보관함 / 저장소를 올려 두는 사이트. | 5주차에 배포 서비스를 연결할 때 쓴다. |
| 배포 / 서버 / 클라우드 | 프로그램을 인터넷에 올려 주소(URL)로 접속하게 하는 것 / 그 프로그램이 돌아가는 컴퓨터 / 빌려 쓰는 컴퓨터. | Streamlit Community Cloud 등으로 URL을 만들어 제출한다. |
| 세션 | 접속해 있는 동안만 유지되는 임시 기억. | 사용자 입력은 세션 안에서만 처리하고 저장하지 않는다. |

## 서비스 기능

| 용어 | 쉬운 설명 | 우리 서비스에서는 |
|---|---|---|
| 이원화 엔진 (Track A·B) | 정확해야 하는 계산은 규칙으로(A), 넓게 찾아야 하는 탐색은 검색으로(B) 나눠 만든 구조. | A: 세액공제 계산, B: 지원사업 매칭. |
| 시뮬레이션 / 시나리오 | 조건을 바꿔 가며 결과를 미리 계산해 보는 것. | 청년을 0~3명 더 채용하면 공제액이 어떻게 달라지는지. |
| 대시보드 | 핵심 숫자와 그래프를 한 화면에 모아 보여 주는 화면. | 예상 감면액, 채용 인원별 절감 그래프, 추천 공고. |
| 기업 프로필 / 정형화된 서식 | 기업 정보를 정해진 칸(업종, 매출 등)에 맞춰 입력받는 것. | 엔진 A·B가 같은 입력을 공통으로 쓴다. |
| D-day | 마감일까지 남은 날수. | 추천 공고마다 표시한다. |

## 크롤링과 API, 무엇이 다른가
- 크롤링: 사이트 화면을 프로그램이 읽어 가져온다. 화면 디자인이 바뀌면 깨지고, 사이트가 막으면 못 쓴다.
- API: 사이트가 데이터를 가져가도록 열어 준 공식 창구다. 항목이 정리되어 있고 안정적이다.
- 그래서 이 프로젝트의 Track B는 크롤링이 아니라 K-Startup·기업마당 API로 공고를 받는다.

## 임베딩은 왜 1단계에서 뺐나
- 목표는 6주 안에 끝나는 시연용 프로토타입이고, 조건 필터와 키워드 점수만으로 상위 공고를 충분히 고를 수 있다.
- 임베딩은 말이 달라도 뜻이 비슷한 공고를 찾는 장점이 있지만, 저장소와 처리 과정이 늘어난다. 시간이 남으면 추가한다.
- 발표에서는 슬라이드 9번 문구를 '조건 필터와 의미 기반 선별'로 고치거나, 임베딩을 실제로 추가해 맞춘다 (`08-deck-sync.md`).

## 예상 질문과 답변 방향
- "AI가 세금을 틀리면?" → 금액은 AI가 아니라 법 조문을 코드로 옮긴 규칙 엔진이 계산하고, 모든 결과에 전문가 확인 문구를 둔다.
- "기존 서비스와 뭐가 다른가?" → 지원사업 추천(나이스비즈인포)과 세액공제 점검(혜움 Tax Curation)은 있지만, 둘을 합쳐 채용·투자 전에 혜택 총액을 미리 계산하는 서비스는 공개 자료에서 확인되지 않았다.
- "개인정보는?" → 필요한 기업 정보만 입력받고 저장하지 않는다.
- "RAG와 그냥 ChatGPT에 묻는 것의 차이는?" → RAG는 먼저 실제 공고를 찾아 그 내용만 근거로 답하게 해서, 없는 공고를 지어내는 것을 줄인다.
